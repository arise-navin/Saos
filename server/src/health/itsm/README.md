# `health/itsm/` — the ITSM rule engine (Phase 4)

Reusable execution infrastructure for the 139-rule ITSM catalogue in
[`../rules/itsm/`](../rules/itsm/), and — since Phase 4 — the declarative
configurations that connect every catalogue rule to an engine. A rule is
**data handed to an engine**, never a function of its own.

```
rules/itsm/catalogue.json ──► catalogue.js (loader) ──► adapter.js (severity words → engine bands)
rules/itsm/parameters.json ─► parameters.js (workbook default → instance → runtime; UNCONFIGURED)
itsm/rules/<engine>.json ───► rules/index.js (validated at load) ──► rule-config.js ($param / $window / $clause / selectors → callbacks)
                                                                          │
   run-context.js (one anchor, named windows)                             ▼
   context.js ──────────────────────────────────► runner.js ──► registry.js ──► engines/*.evaluate(rule, ctx)
     ├─ data-access.js   declared reads, completeness metadata, per-run read cache      ▲
     ├─ capability.js    AVAILABLE / UNAVAILABLE / PARTIAL / UNKNOWN, cached per run    │ comparators.js (named compare /
     └─ findings.js      record · aggregate · configuration · historical · relationship · cross_domain   combine / expand callbacks)
   schedules.js          DECISION 9 — recurring spans → concrete UTC intervals
   engine-key.js         DECISION 8 — the ITSM module key, folded into incremental.engineKeys for `itsm` only
```

The eleven hard-coded ITSM rules still produce the ITSM score. See `../rules/itsm/PHASE5-REPORT.md`.

## The runner

`runITSMRules(ctx, { ruleIds })` evaluates configured rules in dependency
order (`composite.runOrdered`), caching results in `ctx.results` for the
composites. Per rule, in this order and stopping at the first gate that fails:

| Step | Config key | Answer when unmet |
|---|---|---|
| declared UNDEFINED dependency | `undefined_dependencies` | `unavailable` naming it |
| object pipeline (DECISION 5) | `requires_objects` (+ `expected_fields`) | `unavailable` with the step reached: `candidate` → `table_discovery` → `schema_verification` → `capability_confirmation` |
| workbook-named table not in the map | `requires_tables: [{ table, fields }]` | same pipeline, same answer |
| parameters (DECISION 4) | `{ "$param": key }`, `{ "$window": … }` | `unconfigured` naming the keys and the workbook sentence |
| instance values | `{ "$choice": { table, element, label } }` | `unavailable` when the label is not on the instance's choice list (0 or >1 matches) |
| clauses | `{ "$clause": { template, value } }`, `scope: [clauses…]` | — |
| the engine | everything else | the engine's own result |

`variants: [...]` evaluates the base config merged with each variant ("report
the two cases separately", "by group / by type") and merges the results; a
rule is `evaluated` if any variant is. An engine fault is caught and recorded
as `error` — one broken rule never takes a run down, and never passes.

**The field gate.** Before an engine runs, every field the detection reads —
predicate fields, link fields, key / time / text fields and every field named
in a scope or query — is checked on the table it is read from. A platform
query on a field the instance lacks silently matches every row (found on the
validation instance, where `incident.problem_id` / `rfc` do not exist and five
linkage rules produced false FAILs); the gate makes such a rule UNAVAILABLE
(`blocker.kind = capability`, the fields named). A missing *evidence* field is
recorded on the result, not blocking.

**Every result carries** a `blocker` when not evaluated (`kind` in
`BLOCKER_KINDS`: undefined_object · undefined_table · undefined_dependency ·
specification_gap · unconfigured_parameter · instance_value · capability ·
read · input · error, plus the pipeline step / fields / parameters), a
`verdict` when evaluated (`fail` · `pass` · `inconclusive` — a rule whose
config declares a `partial` scope with a *detection gap* never passes), its
declared `scope`, and an `explanation` (parameters used with their source,
kpis, reasons, confidence, population).

**Empty population (Phase 5 closure).** Every evaluated result declares the
`population` it judged — `{ total, judged, unit, basis }` (`engines/result.js`
`notePopulation`) — and, when an engine withholds its judgement over a
population that was there, `undetermined` (`withhold`: below_minimum_volume,
insufficient_history, input_inconclusive). The runner's one verdict decision
(`verdictOf` → `undeterminedOf`) answers `inconclusive`, never `pass`, for an
evaluated rule with no finding when nothing was judged (empty_population,
nothing_judgeable), the judgement was withheld, the population count failed,
or no population was declared at all (the fail-safe). The result then carries
`undetermined { kind, reason }` and a skipped-check entry saying health could
not be established. A finding is still a FAIL; empty data is never a FAIL and
stays apart from UNAVAILABLE and UNCONFIGURED. The one declared exception,
`determinate_when_empty`, is where the workbook makes an empty configuration
population the answer (the `rules_referencing_fields` comparator: "fires only
where routing rules reference the fields"). Per-rule audit:
`../rules/itsm/phase5-empty-population-audit.md`.

## The engine contract

```js
{ key, name, version,
  canEvaluate(rule),          // the rule's architecture names this engine
  prepare(ctx),               // build-once structures into ctx.shared (graph store, resolver, indexes)
  evaluate(rule, ctx) }       // → { rule_id, engine, status, findings, kpis, skipped, coverage, measures, parameters, capability }
```

`status` is `evaluated | unconfigured | unavailable | not_configured | skipped | error`
(`engines/result.js`). None but `evaluated` is a pass, none produces a
finding; a `kpis[]` entry is emitted whether or not a threshold was breached.
An evaluated result also carries `population` (and `undetermined` when the
engine withheld its judgement) — see *Empty population* above.

| Engine (`key`) | Generic mechanism | Phase 4 additions |
|---|---|---|
| `record_predicate` | predicate DSL with encoded-query pushdown | `same_as` / `differs_from` (field-to-field) |
| `aggregate` | count / share / ratio / percentage / average / sum / distribution / **joint_share** (DECISION 2), thresholds with `escalate_at`, `minimum_volume` | `numerator_query` / `denominator_query` count-ratio path (per group, across tables), `window`, `trend` over `ctx.measureHistory` |
| `reference_integrity` | batched resolver, exists / active / state / members-active, completeness gating | — |
| `linkage` | join / anti-join / existence / state over reference and m2m links | estate-level `threshold` on the offending share |
| `configuration` | named readers + placeholders through the DECISION 5 pipeline | named comparators (`comparators.js`): `absent`, `rows_where`, `choice_usage`, `dependent_choice_pairs`, `sla_per_band`, `custom_field_population`, `states_absent_from_sla_conditions` |
| `relationship_graph` | **bounded** per-run edge store (DECISION 11): `parentIN` / `childIN` reads for the referenced CIs only, per-node completeness | `report_ratio`, estate `threshold`, `service_criticality` on path answers |
| `temporal_correlation` | key×time index, window join with dependent-key expansion, interval × schedule intersection, before/after | `mode: schedule_intersection` over **expanded** schedules (DECISION 9), `mode: before_after`, `expand_keys` via the bounded graph, `pairs` on the result for composites |
| `audit_history` | audit / journal / task_sla by population; transitions, counts, gaps | `order_source` → `sys_choice.sequence` (DECISION 10); a literal order is refused; incomplete journal counts are `unavailable` |
| `text_analysis` | normalise, tokenise, frequency, pattern scan (Luhn / Verhoeff), blocked clustering, text budget | **TF-IDF cosine** provider (DECISION 1); `similarity`, `cluster`, `frequency`, `pattern_scan` operations over instance rows |
| `composite` | DAG, topological order, result cache, confidence = min (DECISION 7) | named combinators: `shared_offenders`, `all_breach`, `pairs_by_key`, `rate_by_dimension`, `cluster_to_problem_latency` |

## Severity mapping

Workbook word → engine band, explicit and bijective (`adapter.js`):
`Systemic→SYSTEMIC`, `Critical→CRITICAL`, `High→HIGH`, **`Moderate→MEDIUM`**,
`Low→LOW`. Severity does not modify the ITSM score in this phase (DECISION 6).
