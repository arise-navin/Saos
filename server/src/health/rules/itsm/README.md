# ITSM rule catalogue

The authoritative ITSM health-check rule set, transcribed from
`SAOS_Health_Rules_Tracker_ITSM.xlsx` (sheets `Schema` and `ITSM`). One entry per
workbook row, `ITSM-001` … `ITSM-139`, every cell carried verbatim.

| file | what it is |
|---|---|
| `catalogue.json` | the 139 rules, plus the Schema sheet (fields, severity bands, modifiers, worked examples) and the column → field map |
| `traceability.json` | Excel row → Rule ID → `rules[index]`, machine-readable |
| `traceability.md` | the same table for a person |

All three are **generated** — do not edit them by hand. To regenerate:

```bash
cd server
node scripts/import-itsm-catalogue.mjs /path/to/SAOS_Health_Rules_Tracker_ITSM.xlsx
```

The importer refuses a workbook whose header, Schema field list, rule count or ID
sequence differ from what it expects, and the output is deterministic: the same
workbook produces byte-identical files. `catalogue.json` records the workbook's
sha256 so the source of any given catalogue can be checked.

## Phase 2 — classification and architecture mapping

| file | what it is |
|---|---|
| `architecture-map.json` | one entry per rule (slot, archetype, engine, tables, fields, data requirements, query strategy, compatibility verdict, dependencies, result type, volume, complexity) plus the closed vocabularies and conventions it uses |
| `engine-requirements.md` | the ten reusable engines: purpose, rules, input/output contracts, ServiceNow data, performance, existing code reused, new functionality |
| `dependency-map.md` | rules → data sources → engines → finding types; rule-to-rule and cross-domain dependencies |

`architecture-map.json` is generated from decisions recorded per rule; the two
documents are held to it by `test/health-itsm-architecture.test.js` (the engine
rule lists and the dependency sections must match the map). Three relation
kinds are kept apart in `dependencies`: `consumes_output_of` (hard ordering),
`interpret_with` (report alongside / precondition) and `related` (the
workbook's causal cross-links). None of them merges a rule.

Anything the workbook does not state is `UNDEFINED`, and platform tables
inferred from a concept the sheet names ("assignment rule definitions") are
`candidate_tables`, never `tables`.

## Phase 4 — parameters, decisions, status

- **`DECISIONS.md`** — the approved decision lock (11 decisions). Authoritative; changed only on explicit instruction.
- **`parameters.json`** — one typed declaration per workbook threshold for all 139 rules (108 parameters: 61 with the workbook's stated default, 47 `UNDEFINED`; 58 rules declared parameterless). `workbook_text` is the sheet's own "Threshold / Parameter" sentence. Loaded by `health/itsm/parameters.js`; no default is invented (DECISION 3).
- **`status-matrix.md` / `.json`** — the 139-row status matrix (closure: TESTED 76 · UNCONFIGURED 30 · UNAVAILABLE 33 · ERROR 0), regenerated by `node scripts/itsm-status-matrix.mjs` from the rule configurations in `health/itsm/rules/*.json`, the declarations, the tests, one offline run and the last instance validation. Regenerate rather than edit.
- **`instance-validation.json`** — the last READ-ONLY validation against the configured instance (`node scripts/itsm-instance-validation.mjs`): object existence, schemas, choice lists, audit flags, schedule metadata, table sizes, and one full run with per-rule timing. Metadata and counts only.
- **`PHASE4-REPORT.md`** (the Phase 4 build report) and **`PHASE4-CLOSURE-REPORT.md`** (the closure: decision compliance, ITSM-024 / 129 resolution, dependency and configuration audits, schedules, tests, instance validation, performance, remaining blockers, Phase 5 readiness).

## Phase 5 — integration

- **`PHASE5-INTEGRATION-DESIGN.md`** — the Stage 5A design: where the runner connects, the two status layers, normalisation, consumers, configuration and caching.
- **`SCORING-OPTIONS.md`** — the current ITSM score, why it cannot absorb the catalogue, and the decisions a 139-rule score needs. No model is chosen.
- **`phase5-status-matrix.md` / `.json`** — the 139-row matrix after integration (Phase 4 status kept per row, classification, the ladder, estate and instance outcomes), regenerated by `node scripts/itsm-phase5-matrix.mjs`.
- **`phase5-instance-validation.json`** — the read-only integrated validation on the configured instance: standalone vs integrated comparison, aggregation, performance, reuse. Metadata and counts only.
- **`phase5-empty-population-audit.md` / `.json`** — the closure's empty-population audit of all 139 rules (populated, emptied, and emptied with placeholder parameters), regenerated by `node scripts/itsm-empty-population-audit.mjs`; the script throws on any pass over nothing judged.
- **`PHASE5-REPORT.md`** — the Phase 5 closure report: what was integrated, rule execution, standalone vs integrated, repeat scan, the empty-data fix, the old-11 comparison, configuration, performance, tests, the final matrix, remaining issues, scoring and exit state. Instance evidence is regenerated by `node scripts/itsm-phase5-validation.mjs` (read-only).

## Status: Phase 5 — the catalogue runs inside the Health Checker scan

Every ITSM scan runs all 139 slots through the runner (`health/index.js` →
`health/itsm/integration.js` → `EstateRules.analyze`); findings reach the Health
page, the store and the exports, and `manifest.itsm` carries every rule's state.
The ITSM **score** is still the eleven hard-coded rules' pass rate
(`scopes.js ITSM_SCORED_DOMAINS`) until a scoring model is approved.

## Status before Phase 5: every rule connected; nothing yet reaching the Health page

`health/itsm/catalogue.js` reads the catalogue and the map, `health/itsm/parameters.js`
reads the declarations, and `health/itsm/runner.js` evaluates every configured rule
through its engine. The health engine still runs the eleven hard-coded ITSM rules in
`health/rules.js` (`ITSM-INC-UNASSIGNED` … `ITSM-PRB-STALE`) and scores ITSM in
`health/scopes.js` exactly as before; the only module outside `health/itsm/` that
imports it is `health/incremental.js`, which folds the ITSM engine key into the ITSM
module's incremental key (DECISION 8). Connecting the runner's results to a scan and
to the score is Phase 5.

## Why here and not `health/catalogue/`

`health/incremental.js` hashes every `*.json` under `health/catalogue/` into each
module's engine key. A file added there would move every key and force a full
re-read of every module on the next scan — a behaviour change to the running
checker for data no rule reads. This directory is outside that hash. Moving the
catalogue into it is a Phase 2 decision, made when the engine starts reading it.

## What is transcription and what is not

- Every rule field is the workbook's string, or `null` for an empty cell.
- Field names are the workbook headers in snake_case (`Rule (Exact Wording)` →
  `rule`, `Source Tables / Fields` → `source_tables_fields`); the exact header for
  each is in `schema.columns`.
- `excel_row` is added per rule for traceability.
- `schema.severity_bands[].weight` is the number the band's own description
  states in prose ("Weight 100."); the prose is kept beside it.
- `groups_observed` is the distinct `Group` values in order of first appearance —
  an observation, not a defined dimension list (this workbook defines none).
- Nothing is parsed into codes, integers or enums beyond that. In particular
  `remediation_lane` is free text as written (`"Lane 1 where unambiguous, Lane 3
  otherwise"`), not a lane number. The CMDB catalogue's derived fields (`kind`,
  `track`, `lane`, `systemicKind`) have no counterpart here on purpose: deriving
  them is a later phase's work and a decision, not a transcription.
