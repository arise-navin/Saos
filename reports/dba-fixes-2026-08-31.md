## C-1 — `metaQuery` silently under-counts · FIXED

**Root cause, confirmed live before touching anything:**

```
sys_dictionary?reference=sys_user, sysparm_limit=1000, offset paging
  offset    0: 1000      offset 3000:  999   <-- SHORT, and NOT the end
  offset 1000: 1000      offset 4000:  402
  offset 2000: 1000      offset 5000:    0   <-- the actual end
  offset-paged total = 4401      /api/now/stats count = 4402
```

The loop's terminator was `if (page.length < limit) return { truncated: false }`.
It stopped at the 999, returned 3999 rows, and asserted the result complete.

**Fix** — [`dba-metadata.js`](../server/src/servicenow/dba-metadata.js), in the
primitive, so every consumer inherits it:

1. **Only an empty page ends the walk.** A short page is not a terminator on
   this API. The one other legitimate stop is reaching the authoritative total,
   which is a positive signal rather than an inference.
2. **Keyset, not offset.** `ORDERBY sys_id` ascending with a
   `sys_id>{last seen}` watermark, per ServiceNow's documented guidance for
   walking a large result — offset paging without a stable indexed sort has no
   defined row order between requests and re-scans every preceding page.
   `sys_id` is borrowed into the projection when the caller did not ask for it,
   and stripped from the returned rows afterwards.
3. **Reconciled against `/api/now/stats`.** The count is issued **concurrently
   with the first page**, so reconciliation costs a request but not a round
   trip. `complete` is true only when the rows and that total agree within a
   2-row drift tolerance.
4. `orderBy` now **throws** instead of being silently ignored, because keyset
   ordering is load-bearing and a caller who asked for a different sort and
   didn't get one would read the wrong rows as an answer.

**Verification — the exact reproducing query, live:**

```
metaQuery('sys_dictionary', { query: 'reference=sys_user', max: 8000 })
  -> 4401 rows, complete: true, truncated: false
     pages: 6, terminator: 'empty-page'
     expectedTotal: 4402, countDrift: 1
  -> row keys are exactly ['name','element'] — the borrowed sys_id is stripped

getReferences('sys_user')
  -> inboundCount 4401, inboundComplete true, inboundExpectedTotal 4402,
     inboundCountDrift 1
  -> independent aggregate for the same query: 4402 (delta 1)

deliberately capped walk, max: 1000
  -> 1000 rows, complete: FALSE, truncated: true, shortfall: 3402
  -> "A gap of 3402 row(s) is larger than the 2-row live-drift tolerance,
      so this is a FLOOR, not a total."
```

**On the 1-row gap:** 4402 from the aggregate versus 4401 distinct rows from
the Table API is stable across repeated walks, offset-paged and keyset-paged
alike — the two surfaces do not apply row-level ACLs identically. It is
reported as `countDrift`, not swallowed. A 403-row gap is not drift and can no
longer be reported complete.

**Cost:** a `max: 1` existence probe is still exactly one request (it hits the
ceiling and reports a floor honestly, needing no aggregate). Reads that may have
their COUNT quoted pay one concurrent aggregate request.

**Regression tests** — [`dba-paging.test.js`](../server/test/dba-paging.test.js),
11 tests. The measured page shape `1000,1000,1000,999,402,0` is a fixture, so
the bug is reproducible without a 4,400-row table:

- a short page in the middle does not end the walk (asserts 4401, and
  explicitly asserts `!== 3999`)
- rows are distinct — keyset neither repeats nor skips
- the aggregate total ends the walk without a further page
- the caller ceiling is not exhaustion
- a page with no `sys_id` is refused rather than looped on forever
- collected == aggregate is complete; a 1-row gap is drift; **a 403-row gap can
  never read as complete**; a capped walk reports the correct delta

## H-1 — static scan blind to schemed URLs · FIXED

**Root cause:** `executableLines()` stripped comments with
`line.replace(/\/\/.*$/, '')`. `https://` contains `//`, so every URL was
truncated at its scheme before the hostname regex ran:

```
const H = 'https://dev123456.service-now.com';
  as the scanner saw it:  const H = 'https:      -> zero matches
```

The scan could only ever catch a scheme-less hostname — and a hardcoded
connection string always has a scheme. Its own self-check missed this because
the probe it planted was also scheme-less.

**Fix** — [`no-instance-literals.test.js`](../server/test/no-instance-literals.test.js):
`stripLineComment()` walks the line tracking string state and treats `//` as a
comment only when it is **not inside a string literal** and **not preceded by
`:`**. Still not a JS parser — a false negative is a missed literal the
deploy-time guards still catch, while a false positive would make the suite
unrunnable and get the scan deleted.

**The fix immediately caught a real literal the old scan could not see:**

```
client/src/pages/Dashboard.jsx:81
  <input placeholder="https://dev12345.service-now.com" ...>
```

A form placeholder, not a connection value — but the guard is deliberately
shape-based rather than existence-based, because a real-looking literal is what
gets copied. Rather than add a `placeholder=` exemption (a hole, and a
weakening), the placeholder now reads `https://<your-instance>.service-now.com`,
which carries no instance-shaped hostname and reads better as a placeholder.
The three remaining `service-now.com` mentions in the tree are all in comments
and correctly exempt.

**Strengthened self-check.** The probe now plants every shape a real violation
takes and asserts all are caught: a **schemed URL** (the shape H-1 was blind
to), a bare hostname, a quoted sys_id, and both on one line as a config object
would have them. A second test asserts the comment exemption still holds —
including a comment *after* live code on the same line, which must not hide the
code. The scans are run through the same `executableLines` the real scan uses,
so probe and scan cannot drift apart.

## H-2 — no path to MODIFY a column · FIXED

**Root cause: the third appearance of "routing wired per verb, not per target."**
Add was wired (§46), then remove separately (§47), and modify dead-ended.

**Fix — one routing table, exhaustive over verbs × routes**
([`dba-authoring.js`](../server/src/servicenow/dba-authoring.js)):

`classifyColumnTarget` already read the target once and answered the same way
whoever asked. What was missing was one place saying what each verb then does
with that answer. `COLUMN_ROUTE_DECISIONS` is that place, and
`columnRouteDecision(route, verb)` **throws** on an unknown verb or route rather
than falling through to a default — so a fourth verb cannot silently diverge,
because there is nothing to silently diverge into. `addField`, `modifyField` and
`dropField` are all consumers of it.

**`modifyField` — the safe half, and only that half.**
Source is edited, the workspace is rebuilt offline, the guards run, the app is
installed, and the result is read back — the same pipeline `addField` uses.

| Change | Verdict |
|---|---|
| `label`, `default`, **widening** `maxLength` | performed, via source edit + reinstall |
| `hint` | **refused with the measurement** — see below; the SDK accepts it and it does not arrive |
| **narrowing** `maxLength` | refused — `decrease_column_width`, still gated |
| type change | refused — `change_column_type`, still gated |
| rename | refused — `rename_column`, still gated |

A request mixing safe and refused parts is **refused whole**: a half-applied
change the caller believes was whole is worse than a clean refusal. The refusal
names the real operation and carries `doNotWorkAround`, which explicitly
forbids both hand-editing the source *and* substituting a smaller change that
happens to be permitted.

`modify_column` was added to the operations matrix as the one genuinely
**reversible** schema operation, and deliberately **not** marked `additive` —
the additive entries carry a permanence warning ("effectively impossible to take
back") that is false here. Telling a user that changing a label cannot be undone
would train them to ignore that warning where it is true. `classifyOperation`
now emits a matching `permanence` for `undoReversible: true`.

Also new: `modifyColumn()` in
[`dba-source.js`](../server/src/servicenow/dba-source.js), which edits a column's
options **in place** rather than regenerating the declaration — regeneration
from `sys_dictionary` would silently drop a choice map and a `dropdown` setting,
which the dictionary does not carry in the emitter's shape. It refuses any shape
it does not fully understand.

Registered as `dba_modify_field` (35 dba tools, was 34) with
`mutating: true`, so it writes exactly one ledger row through the existing
orchestrator path. Prompt rule 25 now names all three verbs and states that
routing comes from the target.

**Verification — live, against `x_2002152_nwforge_test_demo`:**

```

  incident                    -> augment
  x_..._nope_not_here         -> create_table

DRY RUN  label + widen 40->120
  route in_scope_source, source edit:
    before: StringColumn({ label: "Name", maxLength: 40 })
    after : StringColumn({ label: "Full Name", maxLength: 120 })

narrowing  maxLength 10  -> stage 'gated', refused: decrease_column_width
retyping   type integer  -> stage 'gated', refused: change_column_type
mixed      label + max 5 -> stage 'gated', refused WHOLE,
                            wouldHaveApplied: [label] (not applied)
absent column 'user_age'  -> "Adding one is dba_add_field"
drop, no confirmations    -> still refused; unmet: escalation, snapshot,
                             typedConfirmation, impactAcknowledged;
                             doNotWorkAround present; no .now.ts steps
```

> **Note on the acceptance's `user_age`:** that column does not exist on
> `x_2002152_nwforge_test_demo`, whose columns are `u_name`, `u_priority`,
> `u_status`, `u_assigned_to`. `u_name` (string, 40) was used as the equivalent
> target.

**The full pipeline, run live end to end** — source edit → offline build →
tier check → whole-app install → read-back → source/instance reconciliation:

```
modifyField(test_demo, { name: 'u_name', label: 'Display Name',
                         hint: '…', default: 'unnamed' })
  emit: dba_preflight -> dba_source_edited -> dba_building
      -> dba_tier_check -> dba_tiers_agree -> dba_installing -> dba_verifying
  installedTo: dev428633.service-now.com
  verification.checked:
    label    requested "Display Name"  onInstance "Display Name"  agrees ✓
    default  requested "unnamed"       onInstance "unnamed"       agrees ✓
    hint     requested "The name …"    onInstance ""              agrees ✗
  sourceAndInstanceAgree: true
  -> ok: FALSE, stage 'verification-failed'
     problems: ['hint reads "" on the instance, expected "The name shown in lists"']

independent raw read after:  { label: "Display Name", default: "unnamed", hint: "" }
```

Then restored through the same tool, proving the reversibility it claims:

```
modifyField(… label: 'Name', default: '')  -> ok: true, stage 'verified'
independent raw read:  { label: "Name", hint: "", maxLength: "40", default: "" }
```

### `hint` — found broken by the live run, then fixed · see §hint below

The install above carried `label`, `hint` and `default` in one column

**Regression tests** —

## M-1 — the execution harness · ROOT CAUSE ISOLATED, FIXED

The report declined to guess a cause. The cause was found, and it is **not the
scheduler**.

### What was measured

A one-shot job instrumented with `gs.info` (syslog is readable over REST, so it
sees what the sink cannot report):

```
NFQ… scope=x_2002152_nwforge
NFQ… isValid=true canCreate=true canWrite=true canRead=true
NFQ… afterSet name=[null] value=[null]      <-- the write did NOTHING
NFQ… insert=48997ce573cfc390a40ef7303ab8b747  lastErr=null
NFQ… reread name=[null] value=[null]
```

**The job ran in under five seconds.** Timeline of the isolation:

| Probe | Result |
|---|---|
| backdated `run_start`, watch `sys_trigger` | no trigger row visible; job "never ran" |
| instance clock vs local clock | agree to the second — no skew |
| `sys_trigger` generally | actively claimed and rescheduled — scheduler alive |
| future `run_start` (+45s) | trigger row appears, then is consumed |
| **backdated, instrumented with `gs.info`** | **executed within 5s; sink insert returned a sys_id; stored row has `name: ""`, `value: ""`** |
| the two reported sys_ids, read back raw | both exist, both blank |

### The cause

1. A `sysauto_script` created over the Table API is born in the REST session's
   **current application** — here `x_2002152_nwforge`. The scope cannot be
   overridden on the insert; `client.js`'s own `assertScopeIntentHeld` refuses
   the attempt and proves it (trap #69). So the job runs **scoped**.
2. `sys_user_preference` is owned by `global` with `update_access: false`. A
   scoped script's field writes to it are **discarded in silence**:
   `canWrite()` answers true, the assignment is a no-op, `insert()` returns a
   real sys_id, and `getLastErrorMessage()` is null. Every signal reports
   success; the row lands empty.
3. The harness polled `name=<sinkName>`, never matched, and timed out asserting
   *"the scheduler is not claiming the job at all"* — the opposite of the truth,
   and a diagnosis that sends the next person to investigate the scheduler.
4. Cleanup queried the **same name it could never match**, found nothing, and
   reported `sinkDeleted: true, leftovers: []` while leaving a blank-named row
   behind on every run. The leak was invisible for the same reason the payload
   was.

This also explains the §38 "~2s" baseline: that measurement was taken when the
session's current application was global.

### The fix

[`execution-harness.js`](../server/src/servicenow/execution-harness.js):

- The wrapper emits a **start marker before the body**, so "never ran" and "ran
  and could not report" stop looking alike.
- It **proves the sink round-tripped** — reads the row back by the id `insert()`
  returned and compares the name — instead of trusting `insert()`.
- It **logs that sink sys_id**, which is the only way a blank-named orphan can
  be deleted.
- When the sink did not round-trip it falls back to **syslog**, the one channel
  a scoped script demonstrably can write, chunked under the measured 4000-char
  `syslog.message` limit and reassembled by sequence. This fires *only* on the
  blocked path: the ordinary path still leaves nothing behind, because syslog
  rows cannot be deleted over REST — which is exactly why §32 rejected `gs.info`
  as the primary channel and why it remains only the fallback.
- Cleanup now reads back **by sys_id**, not by name. The old check queried a
  name a blank-named orphan can never match, so it answered "deleted" without
  looking at the row it was meant to delete. A cleanup check that cannot fail is
  not a check.
- **The timeout names its cause**: `not-started` / `return-channel-blocked` /
  `no-report`, each with a message that does not assert more than was observed.

Consumers now distinguish a harness outage from a genuine unknown:
`detectDbEngine` reports `harnessAvailable` / `harnessFailure`, `recoveryVerdict`
adds `blockedBy: 'execution-harness'` and says so in its headline (the verdict is
still `unknown` and still instructs the caller to treat deletes as permanent —
the safe degradation is kept, and surfaced), and `listIndexes` reports
`failure: 'harness-unavailable'` distinctly from `'script-error'`.

**Verification — the previously-hanging one-shot, live:**

```
runServerScript({ body: "report.probe = 'ok';", timeoutMs: 90000 })
  BEFORE: elapsed 93.7s  ok=false  timedOut=true  report=null
  AFTER : elapsed 11.4s  ok=true   timedOut=false cause=null
          started: true, scope: 'x_2002152_nwforge', channel: 'syslog'
          report: { probe: 'ok', ok: true, elapsedMs: 5 }
          cleanup: { jobDeleted: true, sinkDeleted: true,
                     leftovers: [], updateRowsDeleted: 1 }
```

`elapsedMs: 5` is the script's own measurement: the job was never slow.

**And the two features it had taken down recovered:**

```
detectDbEngine  -> { value: 'mysql', dbName: 'dev428633_1' }   (was null/unknown)
listIndexes('incident') -> available: true, complete: false,
                           definitionRecordCount: 0, zeroMeans present
```

**The leak, cleared.** A sweep for blank-named `sys_user_preference` rows found
**11** — six from the original verification pass (11:37–11:50) and five from
this session's probes (12:08–12:16), all `system=true`, blank name, blank value,
no owning user. All 11 were deleted, along with their 11 orphaned
`sys_update_xml` rows (trap #74), and the absence was confirmed by an
independent query: **0 remaining.**

**Regression tests** —
[`dba-harness-channel.test.js`](../server/test/dba-harness-channel.test.js): the
start marker precedes the body; the sink is proven rather than trusted; the sink
sys_id is logged; the fallback fires only when the sink failed; the generated
script stays ES5; and `readLogChannel` distinguishes started/not-started,
surrenders a blocked sink's orphan id, reassembles out-of-order chunks, refuses
to decode a partial report, and ignores other runs' lines.

## M-2 — `listIndexes` shape inconsistency · FIXED

**Root cause:** the unavailable path returned only
`{ table, available, reason, note }`. A caller following the documented contract
("`complete` is `false`, always") wrote `if (idx.complete === false)` and got
`undefined` — falsy, and therefore silently readable as complete — exactly when
the answer was worthless.

**Fix** — the unavailable path is now built by a pure `unavailableIndexes()` and
returns the **full documented shape**, coherent with each field's meaning:

- `complete: false`, `zeroMeans` present and explaining that nothing was read
- `definitionRecordCount: null` and `indexes: null`, **not** `0` and `[]` — an
  empty array here would be the false zero boundary B-1 exists to prevent, and a
  caller iterating it would report a table as unindexed on the strength of a
  timeout
- `failure: 'harness-unavailable' | 'script-error'` (M-1)
- the success path gained `failure: null` for shape symmetry

**Regression tests** assert every documented field is `!== undefined` on the
unavailable path, that no false zero is returned, and that a harness outage is
distinguishable from a script error.

# Closing the remaining items

The five findings above were fixed and staged. Four items were still open:
`hint`, `widen` (proven only by dry run), the M-1 **write-class audit**, and the
commit. The governing rule for all four:

> **build-accept ≠ install-applied ≠ real.** Every write is proven by read-back.

## §hint — the premise was wrong, and the real cause is cheaper to prove {#hint}

The working theory was a **known SDK build/transform bug fixed in the 4.11.x
line** (the workspace pinned 4.10.1). That is **not what the evidence shows**,
and it is worth recording precisely because acting on it would have been a
version bump that changed nothing.

**What was checked, in order:**

1. **The build artifact, not the instance.** `now-sdk build` writes the exact
   record it will upload to `dist/app/update/sys_documentation_…_u_name_en.xml`.
   Building a column declared

   ```ts
   u_name: StringColumn({ label: "Name", maxLength: 40,
                          hint: "BUILD PROBE HINT", help: "BUILD PROBE HELP" })
   ```

   produces

   ```xml
   <help/>  <hint/>  <label>Name</label>
   ```

   — **empty, before the instance is ever contacted.** So the value is lost at
   BUILD time. No install, and no instance, is involved in the failure. This is
   the cheap decisive test the first pass did the expensive way.

2. **The upgrade, applied and measured.** `@servicenow/sdk` was upgraded
   4.10.1 → **4.11.2** (the latest published, 2026-08-27) and the same probe
   re-run. The build output was **identical** — `<hint/>` still empty.

3. **The package diff, corroborating it.** `@servicenow/sdk-core`'s
   `dist/db/` — where `Table` and `Column` live — is **byte-identical** between
   4.10.1 and 4.11.2. The 4.11.2 changes are in flow, playbook, ATF, table
   definitions and orchestrator dependencies; `@servicenow/sdk-cli` differs only
   in auth and logging. There is no column-documentation fix in that line.

**Conclusion: it is not a version bug, and the upgrade was reverted** — a
whole-toolchain change with no benefit is a risk taken for nothing. The
workspace stays on the pinned 4.10.1.

**The real cause is a SPELLING.** `hint?: string` and `help?: string` are
declared on `Column` and accepted by the build, but they are not what the build
reads. Documentation comes from the `Documentation[]` form, where `label` may be
a list instead of a string:

```ts
u_name: StringColumn({ label: [{ label: "Name", hint: "…", help: "…" }],
                       maxLength: 40 })
```

Built on **4.10.1**:

```xml
<help>DOCARRAY HELP</help>  <hint>DOCARRAY HINT</hint>  <label>Name</label>
```

Verified at build on **both** 4.10.1 and 4.11.2 — so this was never a guess to
be shipped untested; it is measured before a single install, and then proven
live by read-back (see §live below).

**What shipped:** `hint` and `help` are supported, and `emitColumnOptions()`
folds `label`/`hint`/`help` into the one `Documentation[]` literal — carrying the
**current** values of whichever the caller did not ask to change, so setting a
hint cannot blank a label. A label with no hint and no help stays a plain
string, the simplest form that works and the one every generated column already
uses. Six unit tests pin the emitted shape, including that a flat `hint:` option
is **never** emitted.

> A footnote that is its own small lesson: when `hint` was still broken, the
> restore step computed "current" from the **instance**, so restoring `hint` to
> `""` was a no-op — leaving the source declaring a hint the instance did not
> have. Source and instance can diverge through an attribute that does not
> round-trip, which is a second reason never to offer one.

## §M-1 write-class audit — one sibling found, and the class closed {#audit}

M-1 is a **class**: a script dispatched through the execution harness runs in
this application's scope, and a scoped script writing to a `global` table has
its field writes discarded in silence — `canWrite()` true, `setValue` a no-op,
`insert()` returning a real sys_id, `getLastErrorMessage()` null.

**Measured Application Access on every table NHA writes this way:**

| table | create | read | update | delete |
|---|---|---|---|---|
| `sys_user_preference` | **true** | true | **false** | false |
| `sys_update_set` | **true** | true | **false** | false |
| `sys_security_acl` | false | true | false | false |
| `sys_dictionary` / `sys_db_object` / `sys_documentation` | false | true | false | false |

`create=true, update=false` is precisely the shape that yields a row with no
fields in it — and it is true of **two** tables, not one.

**The sweep:**

| Path | Writes | Read-back | Verdict |
|---|---|---|---|
| `execution-harness` sink | `sys_user_preference` (global) | in-script compare + syslog fallback + Node-side delete verified **by sys_id** | fixed earlier this session |
| `transport.createSetForScope` | `sys_update_set` (global) | **none** | **EXPOSED — fixed** |
| `elevation-shim.dispatchElevatedWrite` | ACL / role tables | cross-transport `readTargetByNonce` + `assessOutcomeTier` with a projection-superset guard | already sound |
| `acl-authoring.runAclAuthor` | `sys_security_acl` etc. | cross-transport `verifyAclLive`, field-by-field, with `PLATFORM_COMPUTED` separating a transform from a drop | already sound |
| `impersonation` | caller's target table | in-script only | **strengthened** — Node-side REST `diffWrite` added |
| `script-liveness` | — (generic dispatcher) | sentinel proves it RAN; content is the caller's | n/a |
| `dba-context`, `dba-schema` | — (reads) | n/a | safe |
| **DBA data ops** | REST Table API **from Node**, not a scoped script | `diffWrite` read-back | **not exposed — verified, not assumed** |
| **DBA schema authoring** | SDK install, not a scoped script | `verifyColumn` / `verifyColumnChange` | **not exposed — verified, not assumed** |

**The sibling.** `transport.createSetForScope` created the per-scope update set
from a scoped script and checked only `if (!setId)`. Its own comment ended
*"The read-back is what makes that failure impossible to miss"* — **and there was
no read-back.** A documented intention that was never implemented, guarding a
write to a `create=true / update=false` global table. A silently demoted
`application` would have produced a set that refused every row the sweep later
added, failing at the 403 of trap #72 — far from the cause. It now re-reads the
set over the REST Table API and compares `name`, `application` and `parent`.

**The class is now enforced, not just swept.**
[`scoped-write-readback.test.js`](../server/test/scoped-write-readback.test.js)
scans `server/src` for any module that dispatches a server-side script
containing `.insert()` / `.update()` / `.deleteRecord()` and **fails the build**
unless that module is in a registry naming the read-back that proves its write.
A second test checks each registry entry against the source, because a registry
entry is a claim like any other — and a comment promising a read-back that did
not exist is exactly how this survived. Two further tests pin the specific
fixes: the harness must verify cleanup **by sys_id** (a name query can never
match a blank-named orphan, so it was a check that could not fail), and
transport must read back after its insert and compare `application`.

## §live — hint and widen, proven on the instance {#live}

Both were run on a **fresh throwaway column** so the instance could be left as
found, and both were read back through the raw Table API — never the tool that
made the change.

```
STEP 1  addField(test_demo, { name: 'u_qa_probe', type: 'string', maxLength: 40 })
        -> ok, stage 'verified', route in_scope_source
        raw read: { type: string, maxLength: "40", label: "QA Probe",
                    hint: "", help: "" }

STEP 2  modifyField(… hint, help, maxLength: 200)   — one install, all three

STEP 3  INDEPENDENT raw read-back
        sys_dictionary    : { internal_type: "string", max_length: "200" }
        sys_documentation : { label: "QA Probe",
                              hint:  "QA hint proven by read-back",
                              help:  "QA help proven by read-back" }

        hint landed in sys_documentation.hint  ✓
        help landed in sys_documentation.help  ✓
        widen landed (max_length 40 -> 200)    ✓
        label preserved, not blanked by hint   ✓
```

**On `widen`.** It had been proven only by a dry run and unit tests — the exact
state `hint` was in before `hint` turned out to be broken. It is now proven at
install: `max_length` really is `200` on the instance. Had it not landed, it
would have been refused with the measurement, the same way `hint` was.

> **A caveat about how this run finished.** The network dropped between the
> install and the tool's own verification read, so `modifyField` threw and its
> result was never printed. The work had already landed — the independent read
> above is what establishes that, which is the whole point of not believing the
> writer. The escalation flag was never opened (the failure preceded it) and was
> confirmed `false` afterwards.
