# Vercel frontend, Render backend, Turso database

## Render

Create a Blueprint from this repository using `render.yaml`. It defines a Node 24
web service, installs only server dependencies, and starts `server/src/index.js`.
The backend binds Render's `PORT` on `0.0.0.0`. `/healthz` is the public health probe;
all `/api` endpoints require a bearer access token.

Set these Render environment variables:

- `TURSO_DATABASE_URL`: `libsql://saos-v2-navin-patel.aws-ap-south-1.turso.io`
- `TURSO_AUTH_TOKEN`: a new database token, supplied as a secret in Render.
- `FRONTEND_ORIGIN`: the actual frontend origin, for example `https://your-app.vercel.app`, with no trailing slash. Comma-separated additional origins are supported.
- `API_ACCESS_TOKEN`: generated by the Blueprint. Use its value to sign into SAOS; it is not the Turso token.

Do not put either token in Git or a `VITE_*` variable. Rotate previously shared
database tokens before deployment. Keep one backend instance: settings and task
state include process caches and queues that are not coordinated across replicas.

## Vercel

Keep the Vercel project Root Directory at the repository root. `vercel.json` builds
only `client/`, serves `client/dist`, and rewrites SPA routes to `index.html`.
There is no root `api/` function deployment anymore.

Set `VITE_API_URL=https://YOUR-ACTUAL-RENDER-SERVICE.onrender.com/api` in Vercel's
Production environment (and Preview if needed), then redeploy. This value is public
and baked into the frontend build. Do not use the Render dashboard URL here.
Set the resulting frontend origin in Render's `FRONTEND_ORIGIN` and redeploy Render.

Open the frontend and sign in with `API_ACCESS_TOKEN`. JSON requests, chat streams,
uploads, logs, exports, and audio use the same configured backend and bearer token.
Local development still uses Vite's `/api` proxy to port 4000.

## Persistence and local services

Application records use Turso. Saved PDI/LLM settings and skill settings use the
`app_settings` table when Turso is configured, instead of local `settings.json`.
Existing local settings are not automatically uploaded: save them again in the UI.
The first backend startup applies schema migrations; later startups reuse them.

Render's free filesystem is temporary: uploaded attachment extracts, meeting audio,
and generated SDK workspace files are not made durable by Turso. A persistent disk
or external file store is needed to retain these files. In-memory tasks do not
survive process restarts. The free service can sleep, so its first request can be slow.

Ollama on your PC needs an authenticated HTTPS tunnel/proxy reachable from Render.
Set that URL with `/v1` in LLM settings. Render's `localhost` cannot reach your PC.
The local transcription service also needs a reachable endpoint if meetings are used.

## Verification

1. Render `/healthz` returns `{ "ok": true }` after database initialization.
2. `/api/system/settings` without an access token returns 401.
3. Sign in from Vercel, save PDI settings, and test the ServiceNow connection.
4. Restart Render and confirm settings still load from Turso.
5. Verify chat streaming and exports from the Vercel frontend.
