> **M1** — a single assistant response carried both `content` and `tool_calls`.
> **M2** — the loop re-invoked the model after a text-only response; the second iteration

### Why M1 is ruled out

1. **The WI-8 guard was armed and did not fire.** `server/data/settings.json` at the time of
   the repro: `agent.autoApprove = false`, `agent.holdMutationsOnQuestion = true`.
   `detectQuestionWithMutation` runs on every completion that carries tool calls and records a
   `wi8_question_with_mutation` guard row when it holds. **No such row exists in this session.**
2. **The adapter cannot manufacture the split.** `providers/openaiCompat.js` maps `msg.content`
   and `msg.tool_calls` independently and returns `{ text, toolCalls }` with both preserved. A
   completion carrying both would have arrived at the loop carrying both, and would have hit
   the WI-8 guard rather than the A6 guard.

So the split is real, not an artefact of parsing.

## Why the A6 guard fired on a clarifying question

A6 exists for a measured failure: the model designs something, quotes the right sys_ids, and
then asks permission instead of calling the tool — the turn stalls and looks complete from the
outside. Its own comment states the intended boundary:

> A genuine clarifying question ("which of these two items did you mean?") does not match,
> because it does not ask for permission to proceed.

That boundary does not hold. A6 fires when **all** of: zero mutations this turn, the
assistant's text matches `ASKS_TO_PROCEED`, the user's text matches `IS_DIRECTIVE`, and it has
not already fired. On turn 50:

- `ASKS_TO_PROCEED` matched **`let me know`** — recorded verbatim in the guard payload. That
  pattern was widened deliberately (§32/A3) to catch "Let me know!" closing a stalled design.
  It cannot tell "let me know if you want me to build it" from "let me know **which** incident
  you meant" — both contain `let me know`.
- `IS_DIRECTIVE` matched **`change`**, present literally in "priority ko **change** karke LOW
  kardo".

Both halves fired on a question that was asking the user to *disambiguate a target*, not to
*authorise an action*. The nudge the guard then injected is written for the stall case and is
actively wrong for this one:

> *"You already have what you need. Call the tool now with the values you just described."*

The model did not already have what it needed — the target record was the open question. Told
by the harness that it did, it picked one and wrote to it.

The digest of the folded turn records the model's own view, which is not the harness's:

> **OPEN THREADS** — Need to set impact and urgency to Low for INC0010053 to achieve Low
> priority; **awaiting user confirmation** to apply those updates.

## The approval transition: how `approved` was reached

**There is no approval record.** This is a schema gap, stated explicitly as WI-1 requires.

Approval state today is an unresolved `Promise` held in a process-local `Map`
(`orchestrator.js`, `const live`), keyed by a `crypto.randomUUID()` that exists only for the
lifetime of the turn. When it resolves, the outcome is collapsed into a **single terminal
string** on `tool_events.approval` and `mutation_ledger.approval`. There is:

- no approval table,
- no state history,
- no timestamp of the transition (`tool_events.ts` is written *after* execution),
- **no source or actor field** — nothing distinguishes a user click from any other resolver.

### Every writer of approval state (complete enumeration)

| # | Site | Sets | Reachable when |
|---|----|----|----|
| 1 | `orchestrator.js` — `awaitApproval` timeout | `false` -> `'rejected'` | 5 min elapse with no resolution |
| 2 | `orchestrator.js` — `resolveApproval(sessionId, approvalId, approved)` | caller's boolean -> `'approved'` or `'rejected'` | called by #3 only |
| 3 | `routes/agent.js` — `POST /api/agent/approve` | forwards `req.body.approved` verbatim to #2 | any HTTP client that knows the `approvalId` |
| 4 | `orchestrator.js` — auto-approve branch | `'auto'` | `agent.autoApprove === true` |

`resolveApproval` is exported and has exactly one call site: the HTTP route. The route does no
validation — it forwards `approved` straight through and returns `{ ok }`. No server-side path
sets `'approved'` while `autoApprove` is false; the auto path writes the distinct value
`'auto'`, and the ledger row here reads `approved`, not `auto`, which is consistent with the
checkbox having been off.

### What the evidence can and cannot say

The `approved` on ledger row 27 was therefore produced by an HTTP `POST /api/agent/approve`
carrying `approved: true`. The client is the only known caller, so **a user click is by far the
most likely origin** — the 10.1 s window between the guard row and the executed write comfortably
contains a provider call, a human click, execution and read-back, and the user was actively
watching the session.

But it **cannot be proven from the persisted data**, because nothing records who resolved it or
when. Any process able to reach `POST /api/agent/approve` with the right `approvalId` would leave
an identical row. WI-4 closes this permanently by persisting `approved_source` and `approved_at`.

> **Narrowed by the follow-up sprint (WI-3), not removed.** The endpoint now requires a
> server-minted nonce that is sent exactly once, in the `approval_required` frame of the card it
> belongs to. `user_click` therefore now means **"originated from the rendered card of this
> session"** — knowing an `approvalId` is no longer sufficient, and a wrong or absent token is
> refused with the approval left **pending**.
>
> It is still not proof a human clicked. The token travels in the session's SSE stream, so
> anything with access to that stream has it; and the server is unauthenticated, which is now at
> least confined to loopback by a boot-time check. The caveat stands, with smaller scope.

## Conclusions that drive the fix

1. **M2 is the mechanism.** The ask/act split came from the A6 stall guard re-invoking the
   provider after a text-only completion, not from one completion carrying both.
2. **WI-2's invariant, applied literally, would delete A6.** A6 is a deliberate,
   measurement-driven exception to "a text-only response ends the turn". The fix is not to
   remove it but to make it the *only* such exception, fenced so it cannot fire on a question
   aimed at the user — and to assert that fence in a test.
3. **WI-3's guard is real and already exists (WI-8), and it was not enough.** It only inspects a
   *single* completion. It has to survive the nudge: a turn that has already asked the user a
   question must not be allowed to write later in the same turn.
4. **WI-4 is unblocked and independent.** The approval record does not exist and must be built
   before "who approved this" is answerable at all.

## Follow-up sprint — stall telemetry, and the rule for an A6 successor

### Correction to the premise

The follow-up brief assumed A6 had been removed. It was not: `detectStalledTurn` is alive at
[orchestrator.js](../../server/src/agent/orchestrator.js) and still nudges, still writes
`a6_stalled_turn`. What changed is that it is **fenced** — `detectClarifyingQuestion` runs first
and wins. So the population that "ends silently" is not every stall; it is the subset A6's
patterns do not match. Two ways a turn lands there:

- `ASKS_TO_PROCEED` misses the phrasing. `\bi(?:'ll| will) (?:then )?(?:create|…)\b` wants the
  verb next to the auxiliary, so **"I will create it"** nudges and **"I will now create it"**
  does not. One adverb decides.
- `IS_DIRECTIVE` misses the user's message, so A6 declines regardless of what the model said.

That subset is exactly the interesting one, which makes the telemetry better placed than the
brief assumed rather than worse.

### `stalled_turn_ended`

Fires when a turn ends on text-only prose that asks nothing (`isAskingTheUser` → null) and the
turn changed nothing (`mutatingCallCount === 0`). Written to `tool_events` as a guard row, so it
survives compaction and can be counted with SQL.

The `mutatingCallCount === 0` filter is not in the brief and is load-bearing: without it the
event fires on every successful turn in the session — "Created INC0010060." is prose that asks
nothing — and the rate it exists to measure becomes unreadable.

Every quiet turn end is recorded, because a rate needs a denominator. Each row carries an
`intent` label in `result_status`, so the two populations separate without parsing payloads:

```sql
SELECT result_status, COUNT(*) FROM tool_events WHERE name = 'stalled_turn_ended' GROUP BY 1;
```

- `declarative` — the model announced work and did none. *"I will now create the incident…"*
- `informational` — the model answered and stopped. *"Beth Anglin."* Not a stall; a complete turn.

`stallIntent` is a **label on telemetry and nothing else**. It gates no behaviour, holds no
write, ends no turn. That restriction is the point: A6's nudge was built on a guess about the
model and asserted something false to it, so the rule this sprint adopts is that a guess may
describe a row and may not decide one.

### The decision rule for a successor — recorded, not implemented

No nudge is rebuilt this sprint. The behaviour is now a *recorded decision*: a text-only
response ends the turn, including declarative intent. If `stalled_turn_ended` with
`result_status = 'declarative'` occurs in normal use at a rate that burns real sessions, the
successor is **one** nudge, with these constraints, none of them optional:

1. Exactly this text, or something with no more content than it:
   > *"If you intend to act, emit the tool call; if you need information from the user, ask the
   > question and nothing else."*
2. **Asserting anything about the sufficiency of the model's context is prohibited.** A6's
   *"You already have what you need"* is what turned a clarifying question into a write to the
   wrong record. The nudge may say what to do; it may not say what the model knows.
3. Capped at one per turn.
4. Never fired on asking-classified prose — `detectClarifyingQuestion` keeps precedence, as it
   does over A6 today.
5. Always logged, as A6 is.

The event decides whether it is ever written. `informational` rows are not evidence for it.

## Follow-up WI-1 — sys_id provenance

### The anchor was wrong, and the stop rule was right

WI-1 asked for the registry to extend "the existing compaction carry-across structure (the set
that already survives digests)". **There is no such set.** `replaceSpanWithDigest` deletes from
`messages` and `chunks` and writes one row to `digests`, whose only payload is `text` —
free-form markdown authored by the summariser model.

So the thing that carries identifiers across a fold is prose. Its own prompt says *"A mistyped
sys_id is worse than an omitted one — it will be used"*, and `compaction.js` records a measured
run where a digest enumerated 100+ record numbers and dropped the flow sys_id entirely. A hard
block on writes cannot take its truth from the artefact it exists to police. (Checked fairly:
the one digest in the live database states `INC0010052 — sys_id cfc09cdf…`, which *matches*
`mutation_ledger`. Being right once is not the guarantee a hard block needs.)

Reported before building, per the stop rule. The agreed shape:

### An index, not a second source of truth

`sysid_provenance` (migration 9). Every row is written by the **same call** that writes the
durable record it derives from, so there is one producer per source and nothing to reconcile:

| source | written by | carries |
|---|---|---|
| `tool_result` | `recordToolEvent` | table, `display_id`, `event_seq`, and the **row count of the result set** |
| `user_message` | `appendMessage`, before any fold can reach the message | — |
| `ledger_fact` | consulted on demand inside `checkWriteTarget`, then recorded | — |

It survives compaction for the same structural reason `tool_events` does: compaction touches
`messages` and `chunks` and nothing else.

`row_count` is the cardinality of the **result set**, not the row. A read that returned five
incidents registers five rows of `row_count 5`, which turns "the model picked one of those and
wrote to it" from a shape inferred from prose into a fact the harness can look up.

### What the gate now does

- **absent from the registry → hard block.** No card. The full payload goes to a
  `confabulated_sys_id` guard row because nothing else keeps it. The message is written to be
  recoverable: read the record, use the sys_id that read returns.
- **present, but only ever one row of a multi-row read, and nothing has narrowed it →** bounce,
  naming the siblings. Narrowing is monotone: one unique arrival — a create, a `get`, the user
  naming it — settles a sys_id for the session, and a later broad query cannot un-settle it.
- **otherwise →** the gate, unchanged.

### The M3 derivation is deleted, not duplicated

`ambiguousTarget` scanned the last eight history entries for identifiers and counted them.
Three things were wrong with that, all structural:

- it counted **strings**. "INC0010055 (sys_id 3324…)" is one record named twice — the false
  positive that cost a live round last sprint. The registry answers about *records*, because
  the read that resolved them is where both identifiers were in hand at once;
- it could only see what was still in `messages`, so a compaction erased the ambiguity along
  with the turns that created it;
- it was a second derivation of "which records are in play". Two derivations of one question
  drift.

`ambiguousWrites` now calls `checkWriteTarget` — the same call the hard block makes.

`bfdd8816…` returns `confabulated`. What remains unproven live is only that this model will
ever produce a confabulated sys_id — not that the guard catches one.

### The false block the audit caught — before it shipped

A hard block is only as good as its coverage, so the guard was audited for **false positives**
before being trusted: a fan-out over every mutating tool, tracing where each one's target sys_id
actually comes from and whether the producing read's result shape would register it, with each
claimed gap independently refuted or confirmed.

It found one, and it was severity-1 and completely ordinary.

**`tool_events.result` is not one JSON document.** The harness appends its own blocks to the
tool's output:

```
{…the created record…}
{"verification": {…}}        <- mutation-pipeline.attachVerification
{"capture": {…}}             <- the transport annotation
{"planTimeWarning": …}       <- WI-5
```

`registerFromToolResult` did `JSON.parse` on the whole string, which throws at the second
document — so **every mutation result was silently dropped from the index**. Reproduced before
fixing:

```
whole-string JSON.parse          -> THROWS: Unexpected non-whitespace character after JSON
registerFromToolResult(pure)     -> 1   (row written)
registerFromToolResult(stored)   -> 0   (silent miss)
```

The user-visible consequence: *create an incident* → *"now assign it to the network team"*. The
created sys_id exists in that result string **and nowhere else**, so the follow-up update was
hard blocked as a confabulation. The irony was load-bearing — `sessions.js` says of that very
string that the created sys_id "exists here and nowhere else", and that was the string the index
could not read.

Fixed with `parseLeadingJson`, which takes the first balanced JSON value and ignores what
follows, scanning for balance rather than splitting on newlines because record field values
contain both braces and newlines. Two further tiers behind it:

- **loose ids** — 32-hex strings in the text that are not a structured record's `sys_id`:
  reference fields, ids inside the appended blocks. Registered separately, each with
  `row_count 1`. That separation is the point: a `get_record` returns six reference sys_ids, and
  folding them into the record count would make a unique read look like a six-way choice.
- **truncated results** — `RESULT_CHAR_LIMIT` cuts long reads and appends a marker, which breaks
  the parse. Falls back to a text sweep and **logs that structure was lost**, rather than
  refusing a legitimate write in silence.

The audit also established the hard block's real surface, now pinned by a test that *enumerates*
rather than asserts a list: only `update_record` and `delete_record` take a caller-supplied
`sys_id`. Every create derives its sys_id from the **result**, and the pre-gate call passes
`result = null` — so a create can never be blocked. Adding a tool that takes a sys_id from its
input will fail that test, which is the moment to decide whether a hard block suits it.

```
        blocked: []   bounced: 0   approvals: ["be7c6caf…"]
```

and the registry behind it, read back from the live database:

The reference sys_id did not inflate the record's `row_count`, so the update was `ok` rather

That round also produced the first live `stalled_turn_ended` row — *"The incident already has
Category = Inquiry / Help. No change is needed."*, labelled `informational`. A complete answer,
correctly not counted as a stall.

### What is now known about this failure class

Three distinct mechanisms, all producing "the user is asked to decide something already decided
for them":

| | Shape | Guard |
|---|---|---|
| **M1** | one completion carries a question **and** the write | `detectQuestionWithMutation` — withhold the write, discard it, end the turn |
| **M2** | a text-only question, then the A6 nudge re-invokes the provider, then the write | `detectClarifyingQuestion` fences A6; the continuation ledger makes it the only sanctioned continuation |
| **M3** | a bare write with **no prose**, while two candidates are on screen | `ambiguousTarget` + `detectUnexplainedMutation` — bounce once with the candidates named, bounded at three |

M1 was the original hypothesis and is the one that did **not** happen. M2 caused the reported
incident. M3 was found by trying to verify the fix, and is the one no amount of reading the code
would have produced.
